Flagged as an important finding in the final whole-branch review and recorded here (no code change) rather than fixed, since fixing it would mean moving the backfill into the migration this late in the branch — relevant context for sub-project 2 (Academic Calendar) and later sub-projects that will build on this table.
- **SQLite rewrites sibling FK-reference text when a referenced table is renamed, even transiently — the root cause behind the Academic Calendar sub-project's Task 1 fix round (`cc31119`).** A raw-SQL table rebuild that renames the table being rebuilt away (e.g. `academic_sessions` → `academic_sessions_old`) before dropping it causes SQLite to silently rewrite the FK-reference text embedded in every sibling table's stored `CREATE TABLE` SQL (here: `courses`, `registration_periods`, `academic_holidays`, all of which hold FKs into `academic_sessions`) to point at that transient name. Once the transient table is dropped, those siblings' FK references point at a name that no longer exists — a form of corruption that is completely silent until something tries to join through the FK. The safe pattern (which Alembic's own `batch_alter_table` already uses, confirmed by checking how it handled `semesters` in the same migration): create the replacement table under a brand-new temp name, copy the data across, drop the *original* table by its real, unrenamed name, then rename the temp table into the original's place. Never rename a table that other tables hold FKs into, even as an intermediate step of a rebuild-and-drop sequence. Directly relevant to any future DDD sub-project migration (sub-project 3's `Course`/`CourseOffering` split in particular) that needs to rebuild a table other tables reference.
- **A no-op admin edit-form resubmit silently destroying a filtered foreign-key reference is now a confirmed recurring bug pattern, caught three times across two DDD sub-projects.** Sub-project 1's Programme-Department checkbox list (fixed `e7329eb`), sub-project 2's session-edit Programme dropdown (fixed `c797c91`), and sub-project 2's period-edit Semester dropdown (fixed `e96a549`, final whole-branch review) all had the identical shape: a form re-render sourced its `<option>`/checkbox list from a *filtered* lookup query (active-only in the first two cases, programme-calendar-shape-only in the third), so a resource whose linked foreign key pointed at something no longer in the filtered set had no matching option, and an admin who edited the form without touching that one field would have the browser silently submit a blank/wrong value, corrupting the link with no warning. The third instance was the most consequential — it could silently reassign a *live* registration period's semester, which drives student-facing course eligibility, not just an admin-side relationship. All three fixes used the same shape: union the current value back into the option list when it isn't in the filtered set, label it distinctly in the template, and (as of the third fix) also add a server-side backstop rejecting any posted value not among the actually-offered options — don't just trust the client. **The generalization for sub-project 3 onward: this isn't only a "status-filtered" (active/inactive) risk — any dropdown filtered by shape, category, or relationship (not just active/archived) can hit the same bug whenever the already-persisted value falls outside the current filter.** Actively check for this pattern in any new admin edit form, and consider the server-side backstop the default, not an afterthought.
- **`activate_period()` unconditionally sets the newly-current `AcademicSession.status` to `'open'`** (not just `is_current=True`) — discovered while writing the Task 5 verification script for the Academic Calendar sub-project. This worktree's sole pre-existing session had `status='draft'` while already being `is_current=True` (an unusual but pre-existing combination from earlier seed/test history, not something this sub-project caused). Activating a throwaway test period switched that session away, and switching back via `activate_period()` again correctly restored `is_current=True` but also flipped `status` from `'draft'` to `'open'` — a real side effect of the function, not a script bug, but one that diverged from the exact pre-verification baseline and had to be manually reverted (`status` set back to `'draft'` directly) after the script finished. A reminder that "restore by re-activating the original period" is not sufficient to fully undo a verification script's state changes when the function being tested has side effects beyond the one field you're focused on — always re-diff the *entire* row against your initial snapshot, not just the field the test was targeting.
- **The 3 new "Term" `Semester` rows deliberately deviate from the design spec's stated seed location, same shape as the `ProgrammeDepartment` backfill note above.** The spec (`docs/superpowers/specs/2026-08-04-ddd-academic-calendar-design.md`) describes seeding the "Term 1"/"Term 2"/"Term 3" `Semester` rows inside the Alembic migration itself. The approved plan silently relocated this to `seed_dev_data.py`, mirroring how the 5 `Programme` rows are seeded (and how sub-project 1's `ProgrammeDepartment` backfill was relocated) rather than the migration. Practical consequence: any environment that runs `flask db upgrade` without also running `seed_dev_data.py` has zero `period_type='term'` `Semester` rows, so a term-based Programme's "New Registration Period" form renders an empty, required Semester `<select>` — submitting it fails validation with a message that doesn't explain the real cause (no term Semesters exist yet). Mitigated during the final whole-branch review fix wave: `period_form.html`'s Semester `<select>` now has an `{% else %}` branch showing a disabled "No calendar periods configured for this programme." option when the list is empty, so the failure mode is at least self-explanatory rather than a silent empty dropdown. Flagged as a minor finding in the final whole-branch review; recorded here per the same pattern as the `ProgrammeDepartment` note.
- **The Course/CourseOffering split's migration (`a29d6f0c81e5`) was lower structural risk than the Academic Calendar migration, but the read-path fallout was wider.** The migration itself is a straightforward rename (`courses`→`course_offerings`, preserving every row's original ID so all existing FKs into it kept resolving) plus a new, empty-until-backfilled `courses` master table — it doesn't rebuild a table other tables hold live FKs into the way the Academic Calendar migration's `academic_sessions` rebuild did, so the SQLite rename-away FK-rewrite hazard documented above didn't apply here. What made this sub-project riskier in practice was the *number of independent Python read paths* that silently assumed `Course` still had the old flat shape (department/level/instructor/schedule/session/semester columns) after the split moved all of those onto `CourseOffering` — five were found across Tasks 5, 6, and 8 (`_recompute_credits`, `admin_dashboard.py`, `services/course.py`, `admin_department.py`'s `get_department_detail`, `admin_export.py`'s courses export) plus a sixth in the dev bootstrap script (`seed_dev_data.py`'s `seed_courses()`) — none of which were in any task's file list. **The generalizable lesson for any future model-split/rename refactor in this codebase: `grep -rn 'Course\.' --include=*.py` (or the equivalent for whatever model is being split) across the *entire* repo, not just the files the plan names, and check every hit against the new model boundary before considering the split done.** A plan's file list is necessarily written before the implementer has seen every consumer; treat it as a starting point, not a completeness guarantee, and budget verification time accordingly. Six real, independently-confirmed regressions across three of eight tasks (with the sixth breaking the *entire* dev-bootstrap sequence on a fresh database, not just one read path) is a materially higher gap rate than either of the two prior DDD sub-projects saw, and is worth flagging prominently to whoever runs this sub-project's final whole-branch review.
- **A throwaway verification script can corrupt real baseline data through an *indirect* path, not just by directly mutating rows it meant to test — a variant of the "always re-diff the entire row" pattern already noted above (`activate_period()`/`status`).** Task 8's CSV-import verification step used real, pre-existing `CourseOffering` rows (not synthetic ones) as its "matching existing code" and "mismatched existing code" test cases; the import service's existing-offering-update logic unconditionally overwrote `department_id`/`department`/`level`/`instructor`/`schedule`/`max_capacity` on those rows because the test's throwaway department differed from their original (`None`) `department_id`. Deleting the throwaway department during cleanup — *before* reverting those two offerings' `department_id` back to `None` — left `PRAGMA foreign_key_check` non-clean (2 violations) until caught by re-running the FK check as an explicit final step and restoring the two offerings from the pre-verification snapshot. **Any verification step that exercises a find-or-update code path (CSV import, bulk edit, etc.) against real/pre-existing rows — not just newly-created test rows — needs those specific rows re-diffed against their pre-verification snapshot during cleanup, and `PRAGMA foreign_key_check`/`integrity_check` re-run as the actual last step, not assumed clean because the cleanup script printed success.**
- **The final whole-branch review's theoretical FK/string department-drift risk in `validate_course_eligible` (Task 3's hybrid FK/string matching) was checked directly against `main`'s real dev database before this merge, and does not materialize today.** The concern: `validate_course_eligible`'s FK-tightening compares `department_id` when both sides have it set, bypassing the legacy string fallback entirely — if the FK backfill had ever drifted from the legacy string data (e.g. `User.department_id` pointing at a `Department` whose `name` no longer matches `User.department`'s string value), a student who'd have passed the old string-only check could be incorrectly rejected by the FK-based one. Checked directly against `main`'s real dev database with:
  ```sql
  SELECT u.id, u.department, d.name FROM users u JOIN departments d ON d.id = u.department_id WHERE u.department IS NOT d.name;
  SELECT c.id, c.code, c.department, d.name FROM course_offerings c JOIN departments d ON d.id = c.department_id WHERE c.department IS NOT d.name;
  ```
  Both returned zero rows — no FK/string drift exists on `main`'s real data today, so this risk does not materialize for this merge. Re-check this if `department_id`/`department` (on `User` or `CourseOffering`) are ever suspected to have drifted — e.g. after a bulk admin edit that updates one field but not the other.
- **Two more call sites still resolve "the active period" via the old, non-Programme-aware `RegistrationPeriod.query.filter_by(is_active=True).order_by(id.desc()).first()` query, deliberately left out of scope for this sub-project** (identified in the final whole-branch review, no code change): `services/admin_dashboard.py`'s `get_dashboard_summary` (line 8) and `app.py`'s Registration Oversight default period (line 2606). With per-Programme-scope-group activation now possible via `activate_period()`, several `RegistrationPeriod` rows can legitimately be `is_active=True` simultaneously — one per scope group — so these two call sites no longer mean "the institution-wide active period" (that concept no longer exists as a single thing); they silently mean "whichever scope group's active period happens to have the highest id." Both were correctly left unfixed here: `admin_dashboard.py` has no per-user context to resolve a Programme against (it's an aggregate admin view, not per-student), and the Registration Oversight page has its own explicit period selector, so this default is just an arbitrary (if slightly misleading) starting selection, not an enforcement gate. A future sub-project should decide whether the dashboard should sum metrics across scope groups or show them per-Programme.
- **A Flask `app_context`/Flask-Login verification-harness trap, worth recording given this project's history of harness bugs producing false verification results (see the several entries above about static-grep verification, false "cleanup succeeded" claims, etc.).** `RequestContext.push()` reuses an already-pushed application context for the same Flask app, and Flask-Login caches the resolved user on that context (`g._login_user`). A throwaway verification script structured as `with app.app_context(): <multiple test_client requests as different users>` will silently serve *every* request as whichever user Flask-Login resolved first — even against a brand-new `test_client()` for a different login — producing a false "cross-user data leak" finding, or worse, masking a real one behind an apparently-correct result. The fix: don't wrap multiple different-user `test_client` request blocks inside one shared `app.app_context()`; let each `test_client()` interaction manage its own request/app context instead. Worth checking for in any future verification script in this repo that simulates multiple different users within a single script.
