- **SQLite rewrites sibling FK-reference text when a referenced table is renamed, even transiently — the root cause behind the Academic Calendar sub-project's Task 1 fix round (`cc31119`).** A raw-SQL table rebuild that renames the table being rebuilt away (e.g. `academic_sessions` → `academic_sessions_old`) before dropping it causes SQLite to silently rewrite the FK-reference text embedded in every sibling table's stored `CREATE TABLE` SQL (here: `courses`, `registration_periods`, `academic_holidays`, all of which hold FKs into `academic_sessions`) to point at that transient name. Once the transient table is dropped, those siblings' FK references point at a name that no longer exists — a form of corruption that is completely silent until something tries to join through the FK. The safe pattern (which Alembic's own `batch_alter_table` already uses, confirmed by checking how it handled `semesters` in the same migration): create the replacement table under a brand-new temp name, copy the data across, drop the *original* table by its real, unrenamed name, then rename the temp table into the original's place. Never rename a table that other tables hold FKs into, even as an intermediate step of a rebuild-and-drop sequence. Directly relevant to any future DDD sub-project migration (sub-project 3's `Course`/`CourseOffering` split in particular) that needs to rebuild a table other tables reference.
