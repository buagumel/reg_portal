- **This worktree's dev DB illustrates a subtle migrate-then-seed ordering gap, discovered during Task 5 verification.** When `flask db upgrade` runs on an *empty* database and `seed_dev_data.py` runs afterward (the normal fresh-worktree sequence), the Phase 2 migration's (`42e5946fa0ab`) string→FK department backfill executes against 0 users, so no `Department` rows get auto-created from the legacy `Computer Science`/`Information Technology` strings, and the newly-seeded demo students never get `department_id`/`programme_id` populated. This is why, in this worktree, `seed_programme_departments()` correctly produces 0 links — there are 0 candidate students with both FKs set (all 4 demo students have `department_id=None`, `programme_id=None`). This is expected/by-design per that function's own docstring ("best-effort... not exhaustive — most historical data predates the FK dual-write"), not a bug. It was functionally verified separately by temporarily dual-writing FKs on synthetic copies of the demo students, running the real backfill function, confirming the expected `(programme_id, department_id)` pairs (with correct de-duplication) were created, then reverting. Only `main`'s real dev DB — where migrations have historically been applied against already-populated data, or backfilled via an ad hoc script per the note above — has real `department_id`/`programme_id` linkage today.
- **Task 5 verification found and cleaned up stray test data left in this worktree's dev DB** from an earlier task's live walkthrough testing: two extra `Programme` rows (`TESTPRG`, `TESTPRG1785851270`) and one extra `Department` row (`TESTDEPT`), none of which were part of the standard 5-programme seed set. - **The `ProgrammeDepartment` backfill deliberately deviates from the design spec's stated location.** The spec (`docs/superpowers/specs/2026-08-04-ddd-programme-department-foundation-design.md`) describes the backfill as living inside the Alembic migration itself, mirroring the Phase 2 `Department` string→FK backfill precedent (`migrations/versions/42e5946fa0ab_...py`, which backfills inside its own `upgrade()`). The actual implementation — following the approved plan, which silently relocated it — instead put it in `seed_dev_data.py`'s `seed_programme_departments()`, i.e. dev/seed bootstrap only, **not** in the migration. Practical consequence: any environment that runs `flask db upgrade` without also running `seed_dev_data.py` gets a permanently empty `programme_departments` table until an admin populates it by hand via the Programme detail page's "Assigned Departments" form. Bounded impact — the spec itself calls this backfill "best-effort, not authoritative," and `programmes.manage` (the permission gating that admin UI) is itself only seeded via `seed_dev_data.py` in this repo's existing bootstrap path, so there's no path where the permission exists but the seed script never ran. Flagged as an important finding in the final whole-branch review and recorded here (no code change) rather than fixed, since fixing it would mean moving the backfill into the migration this late in the branch — relevant context for sub-project 2 (Academic Calendar) and later sub-projects that will build on this table.
